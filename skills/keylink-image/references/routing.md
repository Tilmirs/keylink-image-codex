# Routing and compatibility

## API address

Send requests directly to `https://keylinkclub.com`, unless the user explicitly sets `--base-url` or `KEYLINK_BASE_URL`. Do not inherit `OPENAI_BASE_URL`, `OPENAI_API_BASE`, Codex provider URLs, or the CCSwitch local API listener. CCSwitch's Codex listener can return 404 for Images and reject or transform Chat requests. Its current Keylink credential can still be reused without routing any requests through the listener. Model discovery uses the same selected host and does not fall back to other providers. Ordinary HTTP network proxies remain the transport's responsibility.

Credential selection is separate from request routing. An explicit `KEYLINK_API_KEY` wins. Otherwise prefer the Keylink key saved in CCSwitch. For older versions, retain `providers.is_current` selection; respect device-local `settings.json.currentProviderCodex` when present. New routing uses `live-state.json.apps.codex.proxy_route`. Aggregation is active only when `mode` is `proxy` and `stack.enabled` is true: consider that saved route and `stack.members`, not the historical `stack.keys` registry. Match provider API hosts to the request host; use `website_url` only if no remote API endpoint is available. A matching saved key works after the UI exits and when process/listener probes are unavailable; return `ccswitch-saved-provider` or `ccswitch-saved-aggregation-provider` as the credential source without claiming the process is running. Legacy selected providers with only a local forwarding URL still require confirmed running state. Do not assume a default OpenAI account or another provider supplies a Keylink key. Ambiguous matching keys require an explicit default-provider choice or `KEYLINK_API_KEY`, even when CCSwitch is closed. Missing optional proxy/endpoint tables or newer columns must not disable legacy provider reads. These files and the SQLite database are read-only.

If no CCSwitch key is available and its running state is known, check common Codex/Codex++ auth/config locations for account login (`auth_mode` indicating ChatGPT, or populated login token fields). If signed in, stop with `codex_account_detected` and `manual_key_required`: the user must configure and save a Keylink provider in CCSwitch or set `KEYLINK_API_KEY`. Do not reuse account auth/config keys or `OPENAI_API_KEY`, even with `--confirm-codex-auth`. Preserve account login files.

Process/listener probes use three states. A positive probe confirms running. A successful process query without a match and an absent/refused listener confirm stopped. Permission errors, nonzero `tasklist` failures, failed `pgrep` queries (exit 2+), unavailable commands and timeouts leave the state unknown unless the other probe confirms running. Select an unambiguous saved key matching the API host before enforcing this running-state gate. If no such key exists, unknown returns `ccswitch_detection_required` and `requires_host_execution` before any Codex credential fallback. Follow the approved host retry described in `SKILL.md`; never treat saved configuration or unreadable process state as proof that CCSwitch is stopped or running.

If no account login is detected, API-key-only Codex/Codex++ auth/config files and `OPENAI_API_KEY` may be offered as fallback whether CCSwitch is stopped or has no usable key. Return `credential_confirmation_required`, then require confirmation that the candidate belongs to Keylink before retrying with `--confirm-codex-auth`. Reject `PROXY_MANAGED` placeholders and never extract OAuth access, refresh or ID tokens as API keys.

## Automatic endpoint order

| Model family | Text generation | Reference-image edit |
| --- | --- | --- |
| `gpt-image-2` and `gpt-image-*` | Images Generations, then Chat | Images Edits, then Chat |
| `gpt-image-2.5`, `gpt-image-2.5-sunburst`, `gpt-image-2.5-flare` | Images Generations, then Chat | Images Edits, then Chat |
| `gemini-3-pro-image`, `gemini-3.1-flash-image`, and Gemini image IDs | Images Generations, then Chat | Images Edits, then Chat |
| `gemini-nano-banana-2.1` | Images Generations, then Chat | Images Edits, then Chat |
| Other pass-through model IDs | Images, then Chat | Images Edits, then Chat |

Automatic fallback occurs for HTTP errors, successful responses with no image, and image download or decoding failures. Both endpoints use the same model ID, cleaned prompt, requested output size, selected count, and prepared references. Explicit `images`, `chat`, and custom endpoint modes stay on that endpoint.

The `gpt-image-2.5` variants are distinct pass-through IDs, not aliases for `gpt-image-2.5` or `gpt-image-2`. Display only models returned by the current catalog, preserve variant suffixes in every request and saved result, and read published sizes from each variant's own catalog entry. New model names alone do not imply new size support or different API fields.

Images generation uses JSON with `POST /v1/images/generations`. Images editing uses multipart form data with repeated `image` file fields at `POST /v1/images/edits`.

Chat uses `POST /v1/chat/completions`. References are sent both as standard `messages[].content[].image_url` content and as compatible top-level `images[].image_url` values.

The top-level compatibility field initially uses a data URL string, preserving channels that already accept it. Only a 400/422 rejection explicitly naming `images[].image_url` as missing/invalid triggers one retry on the same Chat endpoint with `{ "image_url": { "url": "data:..." } }`. This also handles a JSON `status_code` error wrapped in HTTP 200. Disconnects, 413, unrelated errors and missing-image responses do not trigger a format retry. Do not assume that a required-field error alone proves which schema the channel supports.

## Edit prompts and reference budgets

References determine the operation for both `run` and `start`: `--image` or `--use-last` uses Images Edits first, then Chat in automatic endpoint mode, even with `--mode generate`. Explicit endpoint choices still apply. Prefer `--mode auto` when supplying references. For an independent text-only generation, omit both reference options and use `--mode generate` to disable correction-based last-image reuse.

Only current edit instructions, required image text and preservation constraints belong in the prompt. Exploration defaults to the original workflow, including when the mode is omitted: unwrap explicit JSON `prompt`/`messages`, transcript role blocks, edit headings and tagged context, trim outer whitespace and collapse excess blank lines. Codex may distill rejected ambiguous/overlong input into current edit instructions while retaining required text and constraints. Professional expects a clean final visual prompt prepared by Codex; reject wrappers and preserve valid text including whitespace. Ambiguous remaining context or more than 4,000 edit characters still stops locally. Ordinary generation prompts are preserved. The client never semantically optimizes, translates or truncates prompts.

Default **client budgets**, not claims about Keylink's model limits:

- At most 15 references, longest edge 2048 pixels, no cropping or upscaling. More than 15 stops before submission without discarding any images.
- At most 1 MiB per reference, so up to 15 MiB of prepared files. Compliant small files retain their original bytes; the set no longer shares a 1 MiB budget. If the exact model publishes a lower total budget, compress the largest uploads further as needed. A small file may still need normalization for dimensions/orientation/format or to meet that published total. Always encode from the original and keep reference order. Fifteen full-size inputs occupy about 15 MiB in multipart or 40 MiB in the dual-Base64 Chat format, plus fields/prompt overhead; an undocumented channel limit can still cause 413.
- At most 48 MiB for the encoded request body, including the two Chat Base64 representations and prompt. This client guard accommodates the 15-image policy and is not an advertised server limit. Oversized bodies stop before networking.

The exact selected model's explicit `reference_image_limits` or `input_image_limits`, at the entry root or in `capabilities`, can lower these budgets through integer `max_bytes`, `max_total_bytes`, `max_width`, `max_height`, and `max_images`. Output resolution metadata is never interpreted as a reference limit. When no input limits are published, `reference_limit_source` reports `client-budget`; an undocumented channel may still reject the request with 413.

Pillow validates references and produces separate PNG/JPEG upload copies when needed, preserves alpha for transparent images, applies EXIF orientation, and reduces dimensions/encoding size within the budget. Animated references require an explicit exported frame. If fitting the budget would require excessive detail loss, the client stops and asks for fewer/smaller references. Original files, saved results and confirmed output resolution are preserved. Without Pillow, only recognized small supported images with readable dimensions can pass; references needing normalization stop before submission.

`start` stores durable snapshots under the job directory and records the final prompt, so a worker can continue even when an uploaded file is later moved. `reference_images` reports original/prepared dimensions and bytes; `prompt_info` reports character/byte counts. Completed results record `prompt_mode` (`exploration` by default for new commands; historical records can retain null or an old mode) and the exact `sent_prompt`, including on endpoint failure after a provider response was received; success history, workers, `status` and `last` preserve these fields for display. Started jobs, local body-budget failures, and host network permission failures before any provider response expose `prepared_prompt`, not `sent_prompt`. When all automatic endpoints are blocked by WinError 10013/EACCES, the client releases the selection token for one exact host-permission retry and reports `retryable_host_network_error`; do not refresh the catalog or switch models solely for that retry. A sent prompt does not prove server receipt or generation success; inspect errors and attempt records. Older records lacking full text remain recoverable without fabricating it. Prompts are local user content: do not publish local state files or include them in public diagnostic reports. `request_attempts` records each POST's body size, UTC start time, elapsed seconds and HTTP status, without storing its body or authorization header. Response diagnostics retain field names/types/counts, not image data or message text.

## Sizes

Before each new generation/edit request, query `GET /v1/models` once and have the user choose from that catalog. `run` and `start` require its one-use selection token, bound to the Codex task and API host. Waiting for a reply, entering another chat turn, completing optional design details, or fixing preflight/shell errors before submission does not invalidate an unused token; no time-based expiry is implemented. Keep the same catalog, choices and token for that request. Refresh for a genuinely new request, an explicit refresh, or a missing/replaced/consumed/wrong-host selection, and choose from the refreshed catalog. Check `status` for an existing job; never reset or bypass a used token. Network/host permission selection follows `SKILL.md`: use the permitted route for known restrictions without deliberately failing first, and do not treat HTTP errors as sandbox errors.

`models` also returns `output_count_choices: [1, 2, 3, 4]`, `default_output_count: 1`, `max_output_count: 4`, and exploration/professional `prompt_mode_choices`, `default_prompt_mode: "exploration"` and `prompt_mode_required: false`. Show descriptions once in the user-facing model/count/mode question; optional design preferences are not a required form. Professional authorizes active creative development even for detailed briefs: create a strong concept and develop background, composition, light, material, typography and supporting elements, with positive descriptions and only necessary negatives. Preserve exact required copy, facts, identity and explicit edit locks. Professional searches only Huaban, Gaoding, Pinterest and Dribbble, presents 4 numbered images per batch, accepts numbers or “换一批”, then develops an original design using selected references and user materials. Exploration uses the original generation/edit workflow. Count defaults to the announced 1 and omitted mode defaults to exploration; the model still requires user selection. Do not ask again solely for a missing mode. The CLI defaults to exploration and never auto-optimizes. See [prompting.md](prompting.md) and [professional-mode.md](professional-mode.md). Pass `--count` and `--prompt-mode` to `run`/`start`; counts outside 1–4 stop before credentials, POSTs, token consumption or launch. This Skill limit is separate from the 4 reference candidates and is not a provider maximum claim.

Images Generations uses JSON `n`; Images Edits uses multipart `n`. Chat's `n` is not an image count, so the client makes single-output calls until the chosen count is saved, using identical visual prompt and input references each time. One selection token authorizes this single bounded operation. Automatic fallback remains Images → Chat only before any image is saved. Stop after a partial download failure, a short Images response, or a later Chat error/refusal; return saved images and `requested_count`, `returned_count`, `count_complete` without automatic top-ups. All failed/zero-image endpoints still use the normal fallback policy, and explicit endpoints remain fixed. Detached workers and local recovery preserve the count metadata and all saved images.

The conservative size set is:

- `1024x1024`
- `1536x1024`
- `1024x1536`

For editing, omitted `--size` and `--aspect` inherit the original reference dimensions after EXIF orientation, before any upload resizing/compression. This applies to uploads, `--use-last`, and implicit corrections. Explicit output size/aspect overrides inheritance. Mixed reference dimensions or unreadable dimensions require the user to choose an output size. A non-conservative inherited size still stops for confirmation; it is never silently replaced by a conservative size. Detached jobs keep original dimension metadata and use the same output size through endpoint fallback. New text-only generations still default to square.

`size_source` distinguishes original-reference inheritance, explicit size/aspect, and the text-only square default. Each saved image reports `matches_requested_size` when actual dimensions can be read. A mismatch produces a warning even for Images results: save and deliver the actual returned file, report the discrepancy, and avoid local upscaling or an automatic extra generation.

When the user requests higher resolution, fetch the model catalog first. Present the server-published sizes and label `2560x1440` or `3840x2160` as attempts that the channel may reject when they are not published. Confirmation is required before passing a non-conservative size to `start`.

Before sending `2560x1440` or `3840x2160`, tell the user that high-resolution generation can take several minutes and ask them to wait patiently. Start these requests with the detached job command and poll its status. The worker owns this single job (including bounded sequential Chat calls for multiple outputs) and writes the result after the Codex turn ends; never submit the same selection again.

Do not claim a lower-resolution result is 2K or 4K. Do not retry a confirmed high-resolution request at a smaller size. For Chat results, requested pixel dimensions are advisory and are not guaranteed by the endpoint.

## Response formats

Saving an image and displaying it are separate stages. Codex's image viewer may fail to load a large 4K PNG with an `invalid base64`/`Invalid padding` error even when the file is intact. The client generates a small JPEG display copy with optional Pillow and always preserves the original for delivery and later edits. Preview failures do not trigger endpoint fallback or another generation. `last` recovers saved results without API calls, including results saved by older client versions.

For high-resolution requests, `start` creates a detached worker and returns a job ID. `status` reads the worker's atomic result file and never starts another request. If the Codex task is interrupted while Keylink is processing, resume with the same workspace and thread ID, poll `status`, and then display the saved result. A request started by an older client cannot be reconstructed from the Keylink billing log; use `last` only when the original client actually saved a local result.

`latest-request.json` tracks the current request ID and running/succeeded/failed/refused state. `last` refuses to deliver an older success as the current request's result; legacy tasks also check consumed-selection and job start timestamps. API rejection does not overwrite `last.json`. Explicitly requested historical recovery uses `last --allow-previous` and is labeled `historical: true`, never a new generation. Input preparation and `--use-last` may still read the last successful original for a new edit.

The default `status` rejects a background job superseded by a later request; explicitly querying an old job marks its output historical. Timestamps are compared as instants across UTC/offset formats. State updates use an OS lock released on process exit, and an earlier request finishing late cannot replace the current request's saved reference. If a saved image's history update fails, return the image with `state_recorded: false`; never use endpoint fallback to repeat a generation because of that local state error.

Structured `refusal`, `content_filter`, Gemini `blockReason`/`finishReason` safety blocks, and content-policy error codes are failures even if the response also contains an image field. Inspect the full HTTP error response before truncating diagnostic text; JSON embedded in Chat content and nested response containers must pass the same refusal/API-error checks before extracting images. An explicit provider refusal stops automatic endpoint fallback and model-switch suggestions. Echoed messages with user/system/developer/tool roles are not output images. No prompt is automatically rewritten to bypass a refusal.

Pillow verifies and decodes returned images before saving them as successful results; truncated or corrupt candidates follow the download/decoding failure policy. Without Pillow, validation is limited to image signatures, readable dimensions where supported, and basic completeness checks. Installing Pillow is recommended for complete decoding validation as well as reference normalization.

Model selection writes and consumption share the process-lifetime state lock, so interrupted processes cannot leave a permanent selection lock and concurrent requests cannot consume one selection twice. Background metadata/launch failures release the unsubmitted selection claim. Completed worker results are published before scheduled-task cleanup; a cleanup failure is logged without losing the image or submitting another generation.

The client accepts image URLs, data URLs, Base64 fields, camelCase URL fields, nested Chat text/images, generated image/artifact arrays, Gemini `inlineData`, and image `source.data`. Markdown/HTML image links and bare image URLs are recognized. JSON error envelopes (including `status_code=400/413` inside HTTP 200) remain API errors rather than missing-image errors. Saved files must have recognizable image bytes; an `image/*` header alone is not enough. An image candidate that failed to download/decode is diagnosed separately from a response with no candidate. URL downloads inherit authentication only when the image URL uses the same host as the configured API root, preventing credentials from being sent to unrelated hosts.

If a configured system HTTP proxy fails to connect to a returned image URL, retry downloading that same image directly once before treating the endpoint as failed. HTTP error responses are not retried this way. This download recovery does not issue another generation request or alter model, prompt, size, or endpoint selection.
